# Dexterity EngineProfiles

`handshake_dexterity` is the pure EngineProfiles component of Dexterity, Handshake's internal model switching and launch kernel. It does not rename or implement the existing `hsk.model_lane_run@1`, `hsk.model_lane@1`, or `hsk.model_lane_message@1` contracts.

## Public boundary

An `EngineProfile` bundles its stable `id`, positive `revision`, `Model` content digest and format, `Engine`, named `Preset`, and explicit `Device`. `Registry::new` validates the complete set and rejects duplicate IDs. `Registry::from_json` additionally rejects unknown fields/enum variants and imports at most 1 MiB. `profiles()` enumerates borrowed validated snapshots in ascending profile-ID order for Settings and profile choosers. `resolve(id)` returns an owned immutable `ResolvedProfile`; its SHA-256 fingerprint covers every serialized profile field through the existing canonical JSON asset. Caller mutations cannot change that snapshot. A fingerprint is content identity, not a signature or authorization.

`ResolvedProfile::plan(binding, prompt)` returns a deterministic `LaunchPlan`. The two intended configurations are QAIRT W4A16 Qwen3 0.6B on **NPU**, and GGUF Q4_0 Qwen3-4B-abliterated through llama_cpp on **CPU**, using the registered selector `local/Qwen3-4B-abliterated:Q4_0`. Test digests are synthetic fixture data, not verified weight identities. Supply actual model/bundle digests; no synthetic default profile or installed-model claim is supplied. QAIRT CPU rejects before planning. llama_cpp uses the explicit requested device and requires the host's matching capability; it never substitutes NPU, CPU, or `auto`.

The host supplies `HostBinding`: absolute executable/cwd/data paths, a registered `local/name` QAIRT selector or `local/name:Q4_0` llama_cpp selector, the independently verified registration content digest, explicit runtime capabilities, and the exact environment map. Paths are not opened, resolved or discovered here. The host must verify the selected executable, registration-to-content mapping, actual runtime support, containment and permissions before dispatch. The supplied digest must match the resolved profile. Declared capability is not observed hardware use.

The plan retains the whole resolved profile and fingerprint. Its immutable `arguments()` are separate `OsString` values; the prompt occupies one value following `--prompt`. Never join them into shell text. Execution must clear inherited environment, apply only `binding().environment`, and use the exact supplied executable/cwd. No environment variables, files, network, native libraries or processes are accessed by this library. Plan and binding `Debug` redact prompt, arguments, paths and environment. Explicit getters are privileged data access, not logging surfaces.

`plan(binding, prompt)` retains `OutputContract::ConsoleV1` and its exact existing argv. `plan_with_output_contract(binding, prompt, OutputContract::TestModeJsonV1)` adds exactly one global `--test-mode` before `infer`. `LaunchPlan::output_contract()` identifies the selected contract. `output_contract_fingerprint()` hashes canonical JSON containing `schema: "handshake.dexterity.output_contract@1"`, `profile_fingerprint`, and `output_contract: "console-v1"` or `"test-mode-json-v1"`. This separate digest does not change the profile fingerprint and does not authenticate the full invocation. The host must bind dispatch and control to the same immutable plan, including its prompt and environment, separately.

`TestModeJsonV1` requests a complete JSON result on stderr; it does not make stdout JSON-only or stderr free of diagnostics. The downstream decoder must bound mixed-stderr processing, accept exactly one complete result record with `Error: null` and actual `Profile` counts, and require successful terminal execution plus confirmed reap. Do not invent token IDs or substitute zero usage for missing counts. `Input`, `Output`, and raw streams are sensitive and must never enter logs. This crate adds no decoder, process supervisor, or runtime acceptance claim.

Bounds: profile/model/preset names are 1..=256 UTF-8 bytes, trimmed, without control characters; revisions are nonzero; digests are nonzero 64-character lowercase SHA-256. Token/context counts are positive, output cannot exceed context, context and CLI counts fit signed 32-bit. QAIRT requires a compiled-context bound. Temperature is finite 0..=2; llama_cpp top-k is positive signed-32-bit and top-p/min-p are finite 0..=1. These are this API's conservative accepted ranges, not claims about all upstream options. Sampling families must match their engine. Prompts are 1..=65536 UTF-8 bytes without NUL. Selectors are bounded registered names, never paths, URLs, options, or download instructions.

Settings persistence, authentication, model installation/hash verification, UI, request admission, cancellation, process ownership, actual device observation and typed ModelLane dispatch remain host/owning-component responsibilities. This crate neither launches nor authorizes work. Host integration requires a separate exact published revision adoption and genuine runtime proof.

## Research and reuse

Research basis was provided and inspected by the coordinating author before source implementation; no model was executed for this component. Tagged GenieX sources are authoritative over contradictory prose:

- [GenieX v0.9.3 device.cpp](https://raw.githubusercontent.com/qualcomm/GenieX/v0.9.3/sdk/src/device.cpp), lines 113–140: QAIRT's NPU restriction/coercion; llama_cpp's explicit CPU selection. This component rejects unsupported QAIRT CPU rather than relying on coercion.
- [Tagged run notes](https://raw.githubusercontent.com/qualcomm/GenieX/v0.9.3/notes/run.md), lines 29–47, and [CLI reference](https://raw.githubusercontent.com/qualcomm/GenieX/v0.9.3/docs/en/run/cli/reference.mdx), lines 57–74: device selection and defaults; no implicit default device is adopted here.
- [Tagged CLI flags](https://raw.githubusercontent.com/qualcomm/GenieX/v0.9.3/cli/cmd/geniex/infer.go), lines 70–102: sampling, context, compute, token, think and prompt flags. Existing inspected Tanuki code supplies the global `--skip-update`/`--data-dir` convention. No guessed direct-file mode is implemented.
- Output-contract research pins GenieX commit `7b234f6c2f75c64b64bcbfd24eb47e6dec4028dd`: [main.go](https://raw.githubusercontent.com/qualcomm/GenieX/7b234f6c2f75c64b64bcbfd24eb47e6dec4028dd/cli/cmd/geniex/main.go), lines 101–102, declares the hidden persistent `--test-mode` flag; [infer.go](https://raw.githubusercontent.com/qualcomm/GenieX/7b234f6c2f75c64b64bcbfd24eb47e6dec4028dd/cli/cmd/geniex/infer.go), lines 451–454, wires it into the processor. [common/process.go](https://raw.githubusercontent.com/qualcomm/GenieX/7b234f6c2f75c64b64bcbfd24eb47e6dec4028dd/cli/cmd/geniex/common/process.go), lines 91–99, serializes `Input`, `Output`, `Profile`, and `Error` to stderr; lines 80–88 and 193–212 retain stdout token rendering, and profile printing remains. Select explicit planner-owned transport so downstream dispatch can identify it; reject host-side argument appending, which would alter the declared plan. Existing canonical JSON hashing supplies contract identity. Validate exact argv/default compatibility, contract fingerprints, and preserved binding/redaction through focused source tests; actual decoding, exit/reap and runtime proof remain downstream.
- [llama.cpp presets](https://github.com/ggml-org/llama.cpp/blob/master/docs/preset.md), [LM Studio presets](https://lmstudio.ai/docs/app/presets), and [per-model defaults](https://lmstudio.ai/docs/app/advanced/per-model): named model-specific load/inference settings and explicit precedence. This API resolves one full bundle; it has no ambient override layer.

Inspected extraction inputs: Tanuki's `tanuki-core/src/catalog.rs` and `tanuki-engines/src/geniex.rs`/`process.rs`. Its planner presently hardcodes NPU for both plugins and rejects CPU; that policy was not copied. Its host discovery and supervisor were not copied. The existing `handshake_canonical_json` asset supplies canonicalization and hashing through a dependency, not a host clone. Existing ModelLane navigation owns projections rather than engine configuration, so this is a separate focused component beneath `assets/hskernel`.

The inspected `hsk-studio-worker` owns Studio worker supervision, framed HELLO/request exchanges, null stderr and process reclamation. One-shot streamed inference has a different I/O contract. This source-only unit therefore adds no second supervisor; future execution work must reuse or compatibly extend the owning worker component before host integration. A fork is neither implemented nor justified here.

Risks and controls: declared capabilities may be stale (host verifies before actual dispatch); registrations may change (host rechecks exact content identity); prompts/environment may be sensitive (redacted Debug and no logging); CLI defaults may drift (tagged adapter and explicit arguments); profiles may change after selection (owned snapshot plus full fingerprint). Source planning does not prove any of those external conditions.

## Proof and use

From the asset repository root, the focused source proof is `cargo test --locked --manifest-path assets/hskernel/handshake_dexterity/Cargo.toml`. A fresh standalone crate first needs an owner-authorized lockfile resolution before a locked invocation; none is manufactured here. Keep target/cache output in the owning caller's configured external build root. Owning resource/preparation and independent review requirements apply before execution.

`tests/profiles.rs` uses only the public API: both requested plans, immutable snapshot/fingerprint, strict import, duplicate/missing profile, bounds, CPU-vs-NPU capability rejection, model substitution, unsafe selector rejection, one-argument prompt/redaction, and deterministic repeated planning. These tests do not start models or processes. At initial source authoring, tests had **not been run**; consult the owning proof and publication record for subsequent qualification. This manual alone establishes no compile, runtime, device, publication, Settings or host-dispatch acceptance.

The output-contract extension requires its own focused proof, independent review, publication and exact new host adoption pin. It does not replace or expand the existing `dc053` release proof or change the current host pin; no new test, publication or runtime PASS is asserted here.
