<topic id="research">

The MT-006 source candidate follows current primary implementations inspected on 2026-10-23. [feed-rs 3.0.0](https://docs.rs/feed-rs/3.0.0/feed_rs/) supplies RSS/Atom parsing, encoded-byte input, base-URI resolution and media metadata. Its configurable missing-ID generator lets this adapter distinguish absent provider IDs without generating random identities. [Miniflux discovery](https://github.com/miniflux/v2/blob/main/internal/reader/subscription/finder.go) resolves advertised alternate feed links. [Karakeep ingestion](https://github.com/karakeep-app/karakeep/blob/main/apps/workers/workers/feedWorker.ts) keeps feed-entry associations separate from saved-item identity. [RFC 5005](https://www.rfc-editor.org/rfc/rfc5005) distinguishes feed documents, paging and historical archives. [Atom](https://www.rfc-editor.org/rfc/rfc4287) defines stable entry IDs and link relationships.

Reuse feed-rs and the published rss-acquisition identity/capture/checkpoint boundary. The existing Portal feed worker parses bounded raw bytes, but its fixed entry cutoff does not provide a portable resumable document boundary. Reject a handwritten XML parser, random fallback IDs, provider IDs used as item UUIDs, network credentials inside the crate and assuming one fetched document contains complete feed history.

The selected boundary injects bounded authorized fetching and canonical entry preparation. Parser evidence contains no owned item/member UUIDs. The host prepares existing ObservedEntry records through rss-acquisition and retains the corresponding prepared operations for commit_page. URL-only entries use canonical URL identity; reliable feed entry IDs are namespaced by the selected feed. A continuation binds the document digest and offset, so a changed document rejects resume rather than skipping unseen entries. Host-provided cached bytes are required to interpret an HTTP 304.

Main failure cases are malformed input, changed documents during resume, duplicate IDs, inaccessible links, expired attempts and oversized bodies. Finite limits, exact source/continuation binding, canonical identity reuse and explicit errors address them. Ten parser and eleven provider fixtures pass on Rust 1.97.1, covering RSS and Atom, discovery, encoding, enclosures, unchanged refresh, pagination and failures. Four contract and eleven ingestion cases pass for the affected core extension. The terminal empty archive settles its existing continuation as Partial, preserving earlier items without claiming a complete or empty source. These fixtures do not prove live blog access, host persistence or adoption. Isolated publication and each host's live selected-blog proof remain separate gates.

<topic id="operation">

The package is registered in the RSS workspace. From the repository root, run `cargo test --locked --manifest-path assets/rss/Cargo.toml -p rss-provider-syndication --test parsing`, then the same command with `--test provider`, under the coordinated build owner and preparation gate. No credentials or service are needed for these fixtures. The RSS lock retains all previously pinned package versions; hsscrap and canonical JSON remain published dependencies. Host adoption requires separate live-source and persistence proof.

The host owns current authority, DNS/private-network policy, redirects, credentials, deadlines, cancellation, cached responses, item/stream/member allocation and durable checkpoint publication. Run acquisition through rss_acquisition::acquire so authority is checked before and after provider work. Every actual mutation repeats current authorization and attempt checks atomically in its owning adapter. The configured Source comes from that host's current canonical source record; fetching rejects a changed source configuration under the subscription epoch.

`SyndicationProvider` uses `FetchPort` for bounded bytes and `CanonicalEntryPort` for the existing canonical preparation path. The latter passes explicit reliable IDs as the entry key with the selected source URL as identity namespace; it passes no SourceIdentity for URL-only entries. Preserve original capture URLs, including fragments; canonical hsscrap normalization resolves URL identity separately. `EntryEvidence::populate` fills proposed observation metadata and marks an included inline gallery snapshot Partial without a full-set digest. It does not apply or prove a canonical host gallery transition. Configured source revisions and bounded extensions are validated before fetching, including required-feature rejection. The canonical preparation adapter must persist feed media as Partial evidence through the owning gallery boundary and preserve unmentioned canonical members. Media evidence has no owned IDs: the host allocates ordered members and references and retains their provenance before committing the source batch. Actual host gallery proof remains a later adoption gate.

Schedule only the continuation accepted by the canonical checkpoint and JobQueue::advance. Cursor contents are bounded provider state, not caller authority or an authentication token. The fetch owner durably binds response bytes to the page operation and document URL before entry preparation. A resumed FetchRequest carries the expected digest so the host can select its authorized retained snapshot; substituting changed bytes rejects before further effects. If that snapshot is unavailable, report the failure and recover the canonical job rather than silently claiming completion. Retrying partial owner effects uses the same persisted page/child operation intent. Final nonempty documents report current-document coverage rather than inventing complete historical coverage. HTTP 304 requires host-attested canonical cached bytes for the exact source, document URL and access partition.

Strict RFC3339/RFC2822 publication parsing preserves the original literal and numeric offset. RFC3339 minus-zero and RFC5322 minus-zero offsets remain unknown; known UTC remains distinct. Leap-second literals retain second 60 or remain unknown, never a fabricated normalized second. Ambiguous literals sharing a normalized instant and unknown date formats remain absent; fetch time never substitutes for publication time. Enclosure and MediaRSS evidence retain dimensions, duration, byte size and thumbnails. Complementary records for one URL merge; conflicting observations reject. Package dependencies are feed-rs 3.0.0, scraper 0.29.0, the existing RSS/hsscrap public packages, URL, Chrono, SHA-256 and the workspace's exact Serde versions. Native Cargo metadata resolves the canonical published hsscrap and canonical JSON paths without GUI, server or HTTP runtime dependencies.

<topic id="science-research-and-operation">

MT-007 scientific acquisition research inspected on 2026-10-23: the official [arXiv API manual](https://info.arxiv.org/help/api/user-manual.html), [identifiers](https://info.arxiv.org/help/arxiv_identifier.html), [RSS](https://info.arxiv.org/help/rss_specifications.html) and [Atom](https://info.arxiv.org/help/atom_specifications.html) specifications; [arxiv.py at 09d1b8bc3c85c6334d480fa94c310c3b729b1d01](https://github.com/lukasschwab/arxiv.py/blob/09d1b8bc3c85c6334d480fa94c310c3b729b1d01/arxiv/__init__.py); and installed feed-rs 3.0.0 / quick-xml 0.42.0 sources. arxiv.py demonstrates offset advancement and explicit unexpected-empty failures. Official search counters are OpenSearch `startIndex`, `itemsPerPage` and `totalResults`; no Atom next-link is required. Use conservative official limits of 2,000 entries per request and the 30,000-result query window; the inspected Python wrapper advertises a larger aggregate bound that this adapter does not assume. Refine larger queries or select a separately approved bulk interface.

`science::ScientificProvider` reuses `rss::parse`, `EntryEvidence`, `FetchPort`, limits, scoped continuations and canonical owner preparation. A namespace-aware quick-xml sidecar reads only explicit scientific provenance and API counters that feed-rs does not expose. It rejects DTDs, unknown entity references, duplicate scalar fields, wrong counter namespaces and excessive depth. It does not replace the RSS/Atom parser. `CanonicalScientificEntryPort` is necessary because the existing generic `EntryEvidence` has no extension/provenance field for DOI, version, raw updated literal, source links or publication meaning. Its wrapper preserves those values beside the existing `prepare_entry` intent; the host durably retains them and allocates all IDs. Scientific canonical ports use `ScientificEvidence::populate`, which retains the ordinary source metadata and sets the observation provider to `arxiv`, matching `arxiv/paper/<unversioned-id>`. Raw/versioned entry keys remain unchanged and may differ from that canonical provider ID. Calling `evidence.entry.populate` alone retains the generic `syndication` provider and is rejected by the scientific provider. This is an explicit pre-release Git-revision migration requirement, not a blanket runtime-compatibility claim; generic RSS/Atom metadata is unchanged. Preserve old observations and settled intents rather than relabeling them or retrying old operation IDs with changed metadata. No provider UUIDs or host database schema are created here.

Daily `https://rss.arxiv.org/rss/<categories>` and `/atom/<categories>` are finite announcement views. Explicit approved `https://export.arxiv.org/api/query?...` sources paginate their selected query. There is no automatic daily-to-API switch. Daily publication dates mean announcement dates, including replacements and cross listings. API publication means first submission, while its distinct updated literal describes the returned version. Never substitute update or fetch time for publication. Preserve original OAI/HTTP entry IDs, exact date literals, numeric offset, legacy archive identifiers, explicit versions, DOI, author order, categories and advertised source links. Global paper identity is `arxiv/paper/<unversioned-id>`; source/version appearances remain separate. The host reconciles versions without deleting prior observations.

Hosts enforce current authorization, public network policy, byte/deadline limits, cache ownership, retries and at least `API_MIN_INTERVAL_MILLIS` (3,000 milliseconds) between API requests across jobs and attempts. The existing generic fetch port has no pacing field; the scheduler/fetch implementation owns that policy. Fixtures verify requested offsets and bounded request sequencing, not real wall-clock spacing. Mutable API totals are pinned during a traversal; changed totals, counter mismatch, empty intermediate results or unavailable retained pages reject before further owner effects. Exact digest/offset resumption preserves unfinished pages. Every nonempty daily/API result remains Partial, even after its current query is exhausted. Only explicit zero-result API counters establish a verified empty selected query; an empty daily document does not establish empty scientific history.

The existing Portal `product/portal-server/tests/feed_schedule.rs` fixture uses `https://rss.arxiv.org/rss/cs.AI`. Its prior source/history and legacy identifiers remain untouched. Current Portal generic ingestion takes at most 250 entries and uses account/feed-relative legacy keys; it has not adopted this adapter. Reject replacing retained rows, silently renaming legacy IDs, treating daily update announcements as first submission, copying a Python worker, guessing page counts or claiming immutable full history from an offset search. Host adoption must map retained appearances and canonical paper identity through the owning persistence boundary.

After coordinated test-target/dependency registration, run the owning `science` target in this package under the preparation gate. Eight synthetic cases cover API offsets/digests, scientific provenance, daily/API date meanings, legacy IDs, unchanged paper identity across versions, changed snapshots/totals, missing/wrong counters, rate/expiry/cache failures, scope/epoch admission and partial/zero distinctions. All eight scientific cases, ten existing parser cases and eleven existing provider cases passed locally on Rust 1.97.1. Actual selected-source acquisition, global host reconciliation, durable scientific metadata and scheduler pacing remain separate Portal/Desktop gates. On a typed failure, retain the last committed checkpoint and existing history.
