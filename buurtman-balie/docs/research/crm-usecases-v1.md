# Connected CRM use cases and narrow reuse

Research inspected 11 October 2026. Executable scope is research; analytics below remain proposed. No live sales, warehouse, employee or website usage was acquired. Host identities, stock, checkout, orders, usage and images retain their owners. Rust remains mandatory for the core. Under BB-BOUNDARY-001, hosts provide the canonical GUI in website admin backend panels AND custom software/apps; optional reusable web presentation and host/demo composition belong in a separate crate group from the reusable core. This is the accepted boundary, not a claim that package separation has been implemented or proven.

The first retail context is the operator's camera store, alongside the retained supermarket research. The original operator photo-service website remains a separate host scope; its lifecycle and website stack still require discovery before adapter selection.

Current `src/contracts.rs` exposes workspace authorization, bounded snapshots and revision CAS, not a sales ledger or telemetry warehouse. `src/service.rs` checks snapshot counts/bytes and atomically commits receipts. Portal `product/loom/src/tags.rs` owns profile/account-scoped tag identities, normalized lookup keys and resource assignment separately. CRM string tags cannot be silently treated as those UUID identities. Portal RSS metric/telemetry implementations were not established by the focused source scan; identify their exact owners before integration.

Actual upstream evidence:

- [ERPNext sales analytics source](https://raw.githubusercontent.com/frappe/erpnext/develop/erpnext/selling/report/sales_analytics/sales_analytics.py): document types retain distinct invoice/order/payment semantics, transaction/posting/due dates and permission-aware queries; returns a chart dataset separately. Useful reporting contract, tied to Frappe accounting models; no code adopted.
- [ERPNext stock balance source](https://raw.githubusercontent.com/frappe/erpnext/develop/erpnext/stock/report/stock_balance/stock_balance.py): joins Stock Ledger Entry to Item, groups warehouse/item dimensions, includes opening balances, units and valuation; iterator-based query consumption. Reuse the projection pattern, retain inventory owner.
- [Odoo POS order source](https://raw.githubusercontent.com/odoo/odoo/19.0/addons/point_of_sale/models/pos_order.py): distinct draft/paid/posted/cancelled state, POS sessions and linked refund lines. Daily sales require disposition/refund facts, not merely customer-linked orders. Framework models are not a drop-in Rust core.
- [Frappe HRMS attendance source](https://raw.githubusercontent.com/frappe/hrms/develop/hrms/hr/doctype/attendance/attendance.py): employee/date/shift duplicate validation and overlapping-shift checks; duplicate query uses row locking. Employee context needs an HR owner and separate access contract.
- [PostHog event schema source](https://raw.githubusercontent.com/PostHog/posthog.com/master/contents/docs/data/events.mdx): event name, distinct actor ID, occurrence timestamp and properties distinguish pageviews from query completions. API/capture pages were unavailable to this review; quota, ingestion acknowledgement and query-completeness contracts remain UNVERIFIED and must be inspected before selecting transport behavior.
- [OpenTelemetry HTTP metrics](https://opentelemetry.io/docs/specs/semconv/http/http-metrics/): request-duration histogram in seconds, route/status context and active requests. Operational resource metrics and business feature events need separate meanings.
- [RSS specification](https://www.rssboard.org/rss-specification): GUID identifies source items and may differ from URL; category/date fields describe content. Feed item count is not readership or popularity. [Matomo campaign conventions](https://matomo.org/faq/reports/how-to-build-campaign-tracking-urls/) show explicit attribution and consistent identifiers; private identity must not enter public campaign URLs.
- [OpenTelemetry system metrics](https://opentelemetry.io/docs/specs/semconv/system/system-metrics/): operational CPU/memory/filesystem measures are a separate reference from HTTP activity. CPU time is mode-specific (including idle); define consumed modes explicitly. Inspected system CPU metrics are Development, unlike stable HTTP duration; pin conventions and plan migration. Tenant-attributed usage needs host allocation evidence; whole-machine consumption cannot be assigned to a customer merely because requests carry their identity.
- [Cal.com booking API](https://cal.com/docs/api-reference/v2/bookings/get-a-booking): booking UID, business status, start/end and updated time provide scheduling context distinct from the response's success status. [Immich sharing](https://docs.immich.app/features/sharing/): album viewer/editor permissions and public-link expiry/password/action controls separate asset access from booking state. These are adjacent photo-service references, not selected dependencies or proof of delivery, payment or commercial gallery parity.

Upstream URLs above use moving branches or current documentation; this is dated semantic research, not an immutable release/reuse approval. Pin and re-inspect exact source/license/API revisions before adopting code. Local ownership was rechecked against `src/contracts.rs`, `src/service.rs` and the consuming Portal repository's `product/loom/src/tags.rs`; the latter has account/profile-scoped UUID catalogue validation and a 5000-entry capacity failure, not a silent full-list guarantee.

## Low-cost additions at the future integration boundary

1. A single authorized metric projection envelope: owner/source ID, metric definition/version, unit, window/timezone, cutoff, completeness and drill-through reference. High return because every requested chart reuses it; closes false totals and stale-state ambiguity. Reconcile against each canonical owner, including partial responses.
2. Connected chart-to-record navigation preserving current sale/customer/product selection. Reuses CRM relationships and opaque references; closes fragmented navigation without recreating checkout. Verify exact back navigation and independently authorized target access.
3. Explicit ingestion/interaction event IDs and outcome kinds. Reuses operation-ID/replay discipline; prevents duplicate analytics and separates RSS import from engagement. Replay, late events and suppression/retention need independent owner proof.
4. Shared bounded admission and pressure diagnostics around host storage/analytics transports. Reuses current injected Store/SurrealQuery boundaries; caps swarm fan-out before database overload. Document queue/in-flight/payload limits and test saturation, timeout, lost response and known-operation reconciliation. Never discard uncertain writes or retry changed intent.
5. Privacy-aware projection and receipt recovery design. Reuses workspace authorization and current compliance research; closes HR/analytics exposure and old-payload resurrection risks. Forbidden reads, derived outputs and restored backups must obey the selected host policy.

Chart/component candidates inspected: [Frappe Charts package](https://raw.githubusercontent.com/frappe/charts/master/package.json) declares MIT and a standalone JS distribution, potentially close to current framework-neutral modules. [Vega-Lite package](https://raw.githubusercontent.com/vega/vega-lite/main/package.json) supplies declarative charting with a Vega peer dependency; more useful for rich multi-view exploration, with a larger integration surface. [Twenty UI package](https://raw.githubusercontent.com/twentyhq/twenty/main/packages/twenty-ui/package.json) is MIT but requires React/ReactDOM and component dependencies; defer for this plain-browser module unless a host supplies that runtime. No candidate installed; select an exact revision, inspect API/accessibility/bundle behavior and verify packaging before adoption.

Frappe Charts' inspected package has a placeholder failing test script, so the packaging fit is not a quality verdict. Vega-Lite declares BSD-3-Clause and runtime/example tests. Those declarations are source evidence, not observed passing tests; compare keyboard access, textual alternatives, exact-money display, desktop/mobile layout and actual bundle cost before selecting any chart library.

Full ERP/HR/POS backend adoption is rejected for this embedding boundary: inspected models own accounting, inventory, identity and process state. Reuse report semantics and narrow adapters while preserving original Rust contracts. Current bounded whole-workspace snapshots are not an analytics database; maintain read models with their owners rather than append high-volume telemetry to every CRM snapshot.

## Data races, backpressure and fast responses

The earlier no-specific-CRDT clarification is historical and superseded by accepted BB-CRDT-001 and updated BB-CONCURRENCY-001: the operator explicitly requires CRDT AND data-race tests. [CRDT selection research](crdt-selection-v1.md) proposes a Yrs description-draft boundary; implementation, mergeable scope/owner and proof selection remain unresolved, and no CRDT implementation is claimed. Authoritative CAS/replay, exact money and host stock ownership remain separate from the proposed merge model.

Existing CAS/replay protects logical writes, but does not define transport queue limits or prove swarm response budgets. [Tokio bounded mpsc](https://docs.rs/tokio/latest/tokio/sync/mpsc/index.html) provides capacity/backpressure as a candidate when a host uses Tokio; an unbounded channel does not provide that guarantee. Do not force Tokio into the synchronous core solely for a host admission policy.

Before WP010 execution choose owner-controlled workload size/concurrency, per-workspace/global admission, deadline, payload/response and retry budgets, with overload observable before mutation. Measure p50/p95/p99 plus queue wait, in-flight count, database time, conflict rate and bytes; numeric thresholds remain unresolved and must be selected rather than invented. Separate foreground bounded reads from heavy report exports; specify fairness so one swarm cannot starve another workspace. Unknown commit outcomes retain identical-operation reconciliation.

Next executable integration decision: inspect one canonical host sales or telemetry adapter and finalize its metric envelope, access scope and actual data proof. The research above does not establish Tilroy, warehouse/HR, RSS metric or SaaS analytics compatibility. Compliance research is separately preserved at `repo-governance/docs/research/compliance-v1.md`; its independently reviewed candidates remain future scope.
